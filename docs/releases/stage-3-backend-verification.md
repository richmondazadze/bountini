## Reproduced failure

**P2: a raced rejection can falsely report that a signed operation was rejected.** In `src/app/api/operations/[id]/route.ts:47–63`, PATCH reads the owned operation, conditionally updates `WHERE signature IS NULL`, ignores whether the update affected a row, then synthesizes `{ ...op, status: "rejected" }`. If another request records a signature between the read and conditional rejection, the update affects zero rows but the response still reports rejected. A client may stop reconciliation or offer retry even though the signed operation remains active. The server's active-operation constraint and chain program still prevent unsafe duplicate submission; the response can nevertheless mislead recovery.

Reproduction: `tests/stage-3-backend-contracts.test.ts`, test “reproduces a raced rejection returning rejected when a signature won the conditional update”. The controlled database mock returns an unsigned initial row and zero rows for the conditional update; the actual handler returns rejected without rereading authoritative state. This is a **passing characterization of incorrect existing behavior**, not a desired-behavior regression test. The race was not induced against production.

Proposed coordinated fix: restrict transitions to eligible active statuses, use `UPDATE ... RETURNING`, and return the actual updated/current row. If recording a signature loses a race, reread the persisted signature and refuse incompatible replacement rather than allowing a stale read to decide. Add desired-behavior coverage for concurrent signature/rejection, duplicate signature PATCH, and terminal-state transition races. Keep the response contract and escrow policy unchanged. No server fix was applied during this verification-only handoff.

### Frontend mitigation assessed after the initial finding

Frontend Lead changed the shared `Details` transaction controller to discard the rejection PATCH acknowledgement and GET the persisted operation afterward. It checks identity before and after this recovery read, records the returned signature/status, reloads a confirmed quest, and falls back to `unknown` if GET fails. Unknown/confirming operations disable a new signed action and retain status checking. The main escrow actions use this same controller. The new test “checks persisted signature after a concurrent rejection acknowledgement before unlocking retry” reproduces a PATCH response of rejected followed by authoritative GET of unknown with a signature; the client retains that signature, persists unknown and keeps claim disabled.

Inspected that implementation and ran **48 tests / 5 files**, including Details, workroom, deliverable UI and both added backend verification files: all passed. Existing account/wallet stale-response and broadcast guards remain covered. This mitigation is sufficient for the Stage 3 frontend-only gate because it removes reliance on the erroneous rejection acknowledgement; a later competing action is still checked by the server active-operation guard and Anchor. It does not repair the API contract for other clients or make backend transitions atomic. Preserve the defect and its separate fix recommendation; do not silently label the server race resolved. No backend change is needed or authorized within Stage 3.

## Missing capabilities and frontend constraints

- There is no server draft/upload-list endpoint or cross-device unsaved-workroom-draft recovery. Completed submission history is server-backed; pending editor text/link/file references rely on account-scoped device state. An interrupted local file must be reselected after reload. Do not advertise cloud draft sync or resumable byte-range uploads.
- Messages provide newest-page GET and older `before` pagination, not an `after` delta endpoint or WebSocket subscription. Polling/merging/deduplication and preserving already loaded older pages belong to the frontend. Use sequence/ID identity and never invent unread counts or delivery receipts.
- Upload authorization is checked when the upload starts; a long upload or preparation may finish after access/state/deadline changes. That result is an unsubmitted file/snapshot, not a valid delivery. Operation preparation and Anchor execution independently recheck eligibility. Frontend must discard stale callbacks on account/wallet/access/navigation changes and must not present preparation as confirmed submission.
- Files are private worker deliverables, not public requester/source materials. No public source-file contract exists. Download access needs account membership, not an active wallet connection; signing still needs the exact assigned verified wallet.
- AI does not inspect linked websites/repos. It accepts bounded supported attachments and labels missing/unassessed material. PDF inline viewing, malware scanning, additional revision counts, chat read receipts and automatic payment are not supplied by this backend.
